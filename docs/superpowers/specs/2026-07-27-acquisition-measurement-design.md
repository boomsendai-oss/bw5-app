# 集客計測基盤の整備 — 設計書

- 日付: 2026-07-27
- 起票: TARO指示（計測基盤整備 専任セッション）
- 目的: **集客施策（特にGoogle広告）が、実際に体験予約・入会にどれだけつながったのかを追えるようにする**

---

## 1. 背景と現状（本番DB / GA4 の実測に基づく）

Google広告のパフォーマンス分析（2026-07-27・PMセッション）で、費用対効果が算出できないことが判明した。
本セッションで本番Turso（読み取りのみ）とGA4 Data APIを実査し、原因を4点に特定した。

### 1.1 起票時に判明していた3つの穴

| # | 穴 | 実測 |
|---|---|---|
| 1 | `trial_records.referral_source` に広告/SEOを分ける選択肢が無い | 値あり37件のうち「googleなどのWEB検索」8件に**広告クリックと自然検索が混在** |
| 2 | `trial_records.enrolled_after` が全件0 | 140件すべて0。体験→入会の接続が未記録 |
| 3 | `lstep_friends` に流入元タグが無い | 列は `lstep_id / display_name / … / customer_kana / parent_name` のみ |

### 1.2 本セッションで新たに判明した4つ目の穴

**`status`（来店したか）が実質機能していない。**

| status | 件数 |
|---|---|
| 予約済 | 111 |
| キャンセル | 24 |
| 来店確認済 | **5** |

日次同期のログに「ノーショー候補50人（12時間以上前の予約で『予約済』のまま）」が毎日出ている。
`noshow-candidates` は「運営が手動でLstepのフェーズタグを切り替える」運用を前提に設計されていたが、
**その手作業が実行されていない**。結果、CVRの分母（実際に来た体験）が作れない状態だった。

### 1.3 あわせて判明した事実

- `referral_source` はNULLが103/140件。列追加が2026-07-18のため、**2026-05以降の予約にしか値が入らない**
- `member_id` は140件中53件のみ。直近30日はCSV30行中25行がlstep未紐付 → **lstep_id経由の紐付けは新規客にはほぼ効かない**
- 一方 `applicant_name_kana` は **140/140 埋まっている**
- 体験CSVの取込自体は日次同期で既に自動化済み
- 既存の `/staff/insights` の「体験→入会ファネル」が、メモリにある「体験→月額CVR 51.3%」の出どころ。
  ただし**累計**であり、HACOMONO会員登録数を分母にしているため**月次にも流入経路別にも割れない**

### 1.4 既存バグ

`src/lib/ga4.ts` の `ADS_DAILY_BUDGET_JPY = 200` を使って `/staff/insights` の「広告CPA概算」を
「日予算¥200×経過日数÷広告経由クリック」で計算している。**実際の日予算は¥1,000**（実消化 約¥890/日）なので、
表示中のCPAは**実態の約1/5に過小表示**されている。本設計でGA4の実費用に置き換えて解消する。

## 2. 検証結果 — 設計の成立根拠

### 2.1 カナ突合は実データで成立する

`trial_records.applicant_name_kana` × `boom_members.full_name_kana`（正規化・完全一致）
＋ `enrolled_at` が体験日 −7日〜+90日 の窓に入る条件で検証:

| 検証項目 | 結果 | 意味 |
|---|---|---|
| ヒット数 | 48件（体験48・会員42） | lstep_id経由の10件より大幅に多い |
| 1体験に複数会員がヒット | **0件** | 同姓同名による誤突合は実データ上ゼロ |
| 1会員が複数体験にヒット | 6人 | 体験を2回受けて入会 → 分子の重複要対処 |
| 入会が体験より前 | 1件 | 窓で正しく除外される |

体験→入会の日数分布は**当日入会が18件で最多**、13日以内に大半、最長89日。**90日窓が妥当**。
365日に広げると48→60件に増えるが、増分は誤突合の疑いが濃い。

### 2.2 既存KPIとの整合

このロジックだけで月別CVRを再現したところ、2026-05 50% / 06 57% / 07 50% となり、
**別ソースで集計されていた「体験→月額CVR 51.3%」とほぼ一致**した。ロジックの妥当性の裏付けとする。

なお2026-07-12に報告されていた「6月後半以降HACOMONO新規登録ゼロ」の異常は、
6月14体験→8入会と出ているため**解消済み**と確認した。

### 2.3 GA4に広告費が既に入っている

GA4はGoogle広告とリンク済みで、`advertiserAdCost` / `advertiserAdClicks` が
`date` + `sessionCampaignName` の2次元で正しく日次に分割されて取得できる。
※`yearMonth` 次元は同値が返る（壊れている）。`date` 単独は INVALID_ARGUMENT になり
`sessionCampaignName` の併記が必須（2026-07-27 本番実測。当初この併記要件を書き落とし、
本番で `available:false` になって発覚した）。

14日分の合計 $109.7 → 30日換算 ≈ **¥26,700**。広告管理画面の**¥26,730とほぼ一致**。
クリック数も日次14〜54で30日579クリックと整合する。

→ **Google Ads APIの開発者トークン申請は不要。手入力も不要。** 既存のGA4クライアントにメトリクスを足すだけ。

**制約**: GA4プロパティの通貨がUSDのため費用がドル建てで返る。**GA4管理画面でプロパティ通貨をJPYに変更**して解消する（一度きり・TARO/サイドバー作業）。

### 2.4 目的の出力が得られることの先取り確認

流入経路別の体験→入会（2026-05以降）:

| 流入経路 | 体験 | 入会 | CVR |
|---|---|---|---|
| googleなどのWEB検索 | 5 | 4 | 80% |
| 知り合いからのご紹介 | 12 | 6 | 50% |
| インスタグラム | 4 | 2 | 50% |
| その他 | 6 | 2 | 33% |

**母数がn=4〜12と小さく、現時点では傾向止まりで意思決定の根拠にはできない。**
ただし機構としては目的の出力を生むことが確認できた。
最もCVRが高いのが「広告とSEOが混ざった枠」であり、ここを割る必要性が裏付けられた。

## 3. 設計

### A. status の自動判定（4つ目の穴への対処）

「来店したかを人が打つ」設計を捨て、**実際に発生しているシグナルだけで自動判定**する。

**重要**: `status` 列は**書き換えない**。Lstep CSVが正本であり、書き込んでも次の同期で上書きされてしまうため、
来店判定は**集計時のルール**として実装する。人が下した訂正だけを別列に永続化する。

| 判定 | 条件 | 手作業 |
|---|---|---|
| キャンセル | `status = 'キャンセル'` | 既に発生している（顧客/スタッフがLstepで実行・24件記録あり） |
| ノーショー | `attendance_override = 'noshow'` | 訂正ボタンを押した時だけ |
| 来店（みなし） | 上記いずれでもなく `reserved_at < now` | ゼロ |
| 予約済 | 上記いずれでもなく `reserved_at >= now` | ゼロ |

- Lstepの「来店/来場」列は**打たれていれば尊重、打たれていなければ来店扱い**。
  既存の `resolveStatus`（`trial-import/route.ts`）はそのまま変更せず、実際に打たれた5件も上記ルールで来店に入る
- `/staff/trials` に「ノーショーにする」1クリック訂正ボタンのみ残し、`attendance_override` に書く
  （**使わなくても壊れない**／再取込でも消えない）
- 日次同期メールの「ノーショー候補」通知は**廃止**（毎日ノイズを出して誰も消化していない）

**受け入れた副作用**: 無断ノーショーが分母に混ざるためCVRは実態よりやや低く出る。
ただし**全流入経路に等しくかかる**ため、経路間の比較という本来の目的には影響しない。

### B. 体験→入会の自動突合（Phase 2）

**実行タイミング**: 日次同期の中。ただし**会員CSVが揃った時のみ**（既存の誤退会防止ガードと同じ思想）。手動再実行も可能にする。

**突合ルール**

1. `applicant_name_kana` と `full_name_kana` を正規化（スペース・全角空白・中点を除去）して**完全一致**
2. `enrolled_at` が **体験日 −7日 〜 +90日** の窓に入る
3. 同一会員が複数の体験にヒットした場合は**最初の体験**に紐づける（流入経路の起点を正しく取るため）
4. 1つの体験に複数会員がヒットした場合は**確定させず保留**にして画面に出す（現状0件だが将来の同姓同名に備える）

**スキーマ変更** — `scripts/migrations/20260727_trial_enrollment_match.sql`

| 列 | 型 | 用途 |
|---|---|---|
| `enrolled_after` | INTEGER | 既存。0/1（CVRの分子） |
| `enrolled_member_id` | INTEGER | どの会員に紐づいたか（監査・解除用） |
| `matched_by` | TEXT | `kana_auto` / `lstep_link` / `manual` — 根拠を残す |
| `matched_at` | TEXT | 突合時刻 |
| `attendance_override` | TEXT | §A の来店訂正。`'noshow'` または NULL |

- **`matched_by='manual'` の行は自動突合が上書きしない**
- 過去分も同じロジックで一括バックフィル（48件が埋まる）

### C. 流入経路の計測（Phase 1・併用方式）

自己申告だけで「広告 vs 自然検索」を分けることはしない。
**一般のお客さんはスポンサー表示を見ても区別を認識していない**ため、選択肢を割っても誤答が増えるだけで、
かつ過去分に遡れない。技術側を主軸に据える。

| | 役割 |
|---|---|
| **Lstep流入経路タグ（主軸）** | 広告用の友だち追加URLを1本発行しタグを自動付与。自己申告ゼロで広告経由が確定。**穴3も同時に埋まる** |
| **自己申告（補助）** | 選択肢を「人が正しく答えられる区分」に整理。Googleは割らず、認知チャネル（紹介/インスタ/ネット検索/マップ/チラシ・看板/その他）として使う |
| **GA4** | `sessionSourceMedium` で広告/SEO/インスタのセッションとLINEクリックを取得（実装済） |

**アプリ側**: 流入経路の正規化テーブルを持ち、**旧選択肢と新選択肢の両方を同じ経路に寄せる**（過去データを捨てない）。

**未確認の前提**: Lstepの現在のプランで流入経路機能が使えるか。→ サイドバー指示書で確認する（§5）。
**使えなかった場合のフォールバック**: 広告のリンク先を専用の友だち追加URLに分け、追加時アクションでタグを付ける。それも不可なら自己申告＋GA4のみで運用する。

### D. ファネル画面（Phase 3）— `/staff/insights`

```
2026年7月
  広告費         ¥26,730        ← GA4 advertiserAdCost（JPY化後）
  広告セッション      77        ← GA4 sessionSourceMedium = google/cpc
  LINEクリック        10        ← GA4 line_click
  LINE友だち追加      25        ← lstep_friends（タグ導入後は「うち広告N人」）
  体験予約            12        （キャンセル3）
  入会                 4        CVR 50%
```

下に**流入経路別テーブル**（経路 / 体験 / 入会 / CVR、広告行のみCPA）。

**既存「体験→入会ファネル」との関係**: 両者は分母が違うため**併存させ、ラベルで明確に区別する**。

| | 分母 | 粒度 | 用途 |
|---|---|---|---|
| 既存ファネル | HACOMONO会員登録者（＝実際に来店した人） | 累計 | 来店→入会の精度が高い |
| 新ファネル | 体験予約（キャンセル除く） | **月次 × 流入経路別** | **投資判断に使う** |

**CPAの但し書き**: 流入経路タグが入るまでは「広告経由の入会」を特定できないため、
当面CPAは *広告費 ÷ 広告経由のLINEクリック* までしか出せない。タグ導入後に *広告費 ÷ 広告経由の入会* へ精度が上がる。
**この但し書きは画面上にも表示する**（過大評価を防ぐため）。

**実装上の注意**: `src/app/staff/insights/page.tsx` は既に1036行ある。
ファネルは**独立したコンポーネントとして切り出し**、page.tsx をこれ以上肥大させない。

## 4. 数値定義（画面と集計で統一する）

- **体験（分母）** = `status <> 'キャンセル'` かつ `attendance_override IS NOT 'noshow'` かつ `reserved_at < now` の `trial_records`
- **入会（分子）** = 上記のうち突合が確定した（`enrolled_after = 1`）もの
- **CVR** = 入会 ÷ 体験
- **月次の帰属** = **体験日（`reserved_at`）の月**に集計する（入会日の月ではない）。施策の効果を打った月に帰属させるため
- **広告費** = GA4 `advertiserAdCost` を `date` + `sessionCampaignName` の2次元で取得し月内合計（`date`単独はAPIが受け付けない）
