# 月次締めの自動化 — 設計 (2026-08-28)

WS P（経費見える化）／経理部セッション。TARO承認済み。

## 何を解こうとしているか

TAROの要望は「給与・スタジオ料・経費の月次締めをワンボタン、できればボタンを押すことすら
不要にしたい」。

ただし調査の結果、**問題は自動実行が無いことではなかった**。本番DBの実測（2026-08-28）:

| 項目 | 状態 |
|---|---|
| 売上（hacomono課金） | 8/27まで取込済み（daily_syncで自動） |
| 給与 | 8月は draft ¥428,000。7月確定実績は ¥281,500 |
| スタジオ料 | **3・6・7・8月が1件も生成されていない** |
| 経費・銀行明細 | **2026-06-30で停止**（7月・8月が空） |
| 月確定 | 6月が最後 |
| 経理系の定期実行 | **GitHub Actions 17本中0本** |

そして8月draftの ¥428,000 は「マスタどおり全部開催された前提」の数字で、実績とは合わない。
**アプリの自動計算が実績と合わないので、毎月人間がGoogleカレンダーを見て作り直していた。**
7月の `payroll_lines` に `source='calendar'` の行があるが、これを生成するコードはリポジトリに
存在しない＝手作業でDBに入れられたもの。

したがって、いま cron を足すと**誤った数字が毎日自動で出るだけ**になる。
先に「計算の入力が実績と合っていない」を直す。

## 根本原因

`payroll-calc.ts` と `studioBilling.ts` は、どちらも `lesson_instances`（月確定済みの月）
または `lesson_master` の週次展開（未確定の月）を入力にしている。しかし実績は次の理由でズレる。

1. **会場が週替わり**（水・金）。8/26・8/27 は戦災復興記念館で、`lesson_master` の固定会場では出ない
2. **戦災復興記念館は `studios` に存在しない**。生成しても金額が付かないか別会場に化ける
3. **休講はカレンダーに残る（意図的な運用仕様・TARO確認済み 2026-08-28）**。
   `休講【YURI】長町WAACK 入門🔰` / `【休講】TARO hiphop 中級`（6〜8月で3件）。
   削除しないのは ①生徒が定期的にカレンダーを見るので「今日は休講」と分かる方がよい
   ②あとから「元々無かったのか、休講になったのか」を区別できないと計算ができない、の2つの理由。
   **この運用は変えない。取込側が「休講」を判定して弾く。**
4. **日曜AZUMAの開催クラス数が週ごとに変わる**。クラス編成が動いているのではなく、
   **インストラクターの都合で休む回が出るのを都度調整している**（TARO確認済み）
5. **代講の単価はマスタに無く、その都度TAROが決めている**（TARO確認済み 2026-08-28）。
   `【Ryuki】キッズ HIPHOP 代講 KOKEKO` のような回は、担当した講師へ支払う金額を
   自動計算では出せない。→ **代講と判定した回は金額を推測せず「金額待ち」としてキューに出す**

真実は `boom.sendai@gmail.com` のGoogleカレンダー（人間が編集）。
`location` は入っており、`start`/`end` から実時間も取れる。

## 方針

**Googleカレンダーの実績を `lesson_instances` に取り込み、`lesson_instances` を
「予定表」から「実績台帳」に変える。**

給与・スタジオ料・月確定・KPI・HACOMONO同期は**すべて既に `lesson_instances` を見ている**ので、
ここが正しくなれば全部が一度に正しくなる。

**給与の計算ロジック（`payroll-calc.ts`）には一切触らない**ため、Phase 1 で積み上げた給与保護
（A-1〜A-6・M2〜M18）の回帰リスクを負わない。`studioBilling.ts` は実費型を足すために触るが、
既存の `hourly` / `block` の計算式は変更しない。

正本カレンダーは人間専用でアプリは書き込まない（アプリの同期先は別カレンダー）ため、
**一方向**で完結し双方向同期の衝突は起きない。

### 採らなかった案

- **計算源を個別にカレンダーへ切り替える**: `payroll-calc.ts` と `studioBilling.ts` の両方を
  改修することになり、金額ロジックの回帰リスクが増える。月確定・HACOMONO同期・KPIは
  古い入力のまま取り残される
- **今のロジックのまま cron を足す**: 誤った数字を量産するだけ

## スタジオを2種類に分ける

3ヶ月・108コマの実測で、会場は12箇所に収束していた（「市民会館がいっぱいあってランダム」ではない）。

| 種類 | `pricing_model` | 対象 | 金額 |
|---|---|---|---|
| 計算型 | `hourly` / `block`（既存） | GOAT / T's / AZUMA / K / 長町コナスポ / マイダンスショップ / 七ヶ浜国際村 / **アクアスタジオ** / **LSC・Lスタジオ** | 料金体系はDB済み。カレンダーのコマ数から自動計算 |
| **実費型** | **`actual`（新設）** | 戦災復興記念館 / 宮城野区文化センター / 仙台市民会館 / 七ヶ浜中央公民館 / エルパーク仙台 | **実額を1回だけ記録。計算しない** |

区分の基準は「公共施設かどうか」。**LSC・Lスタジオは公共施設ではないので計算型**（TARO判断）。
`studios` 未登録なので時間単価の登録が要る。
**アクアリーナは `studios` に「アクアスタジオ」(id8・¥440/h) として登録済み**で計算型。
七ヶ浜アクアリーナ内の施設で、同一とみなしてよいかTARO確認待ち。

**Web検索で公共施設の料金を取ってくる案は採らない。**

1. 公共施設の料金は「部屋 × 時間区分 × 平日/休日 × 冷暖房費 × 附属設備 × 市民/市外 ×
   営利/非営利」の多次元で、ダンススクールは営利利用の割増対象になることが多い。
   一般料金表をそのまま使うと桁が変わる
2. 取ってきた値の正しさを確認する手段が「請求書を見る」しかない。なら最初から請求書を見る方が速い
3. 予約時に金額は確定し領収書・請求書が出る。**実額が手に入るものを推測する理由がない**
4. 推定値が「本物の数字の顔をして」PLに混ざるのは、経理で最も避けるべきこと

「入退室の前後30分」「30分刻みで借りられる/借りられない」の問題は、**金額を直接記録すれば消える**。
時間から料金を逆算しようとするから複雑になるので、逆算をやめる。

金額の入力先は **`/staff/studio-billing` のクイック入力**。カレンダーから日付・会場・コマ数は
自動で埋まるので、TAROは金額を入れるだけ。月5〜6件。
**未入力は「金額待ち」として明示し、¥0で静かに埋めない。**

⚠️ 金額を公開カレンダーに書く案は不可。公開ICSを実測したところ `DESCRIPTION` が256件
そのまま配信されており、生徒に会場費が見える。

## 同期アルゴリズム

対象月について:

1. `expandMasterSlots` でマスタの予定枠を展開する
2. カレンダーから同月のイベントを取得し、装飾除去 → 休講判定 → 講師名 → 会場名を解決する
3. 各予定枠に対応するカレンダーイベントを探す
   - **見つかった** → `lesson_instances` を upsert（`status='scheduled'`、
     **会場と講師はカレンダーの値で上書き**、実時間は `start`/`end` から）
   - **見つからない** → `status='removed'` で upsert
     （これをやらないと master 週次展開が休講分を埋め戻して給与が付く）
4. どの予定枠にも対応しないカレンダーイベント（単発WS・バトル練習会・代講）
   → `master_id=NULL` の instance を作る。冪等キーは `calendar_event_id`

`buildExpandedKeys` が (master_id, date) で展開を抑止する既存の仕組みにそのまま乗る。

### 過去日のみ同期する

`lesson_instances` は HACOMONO 枠生成とGoogleカレンダー同期の入力でもある。
未来日を書き換えると **HACOMONO の予約枠が消える事故**につながる
（STATE: 「HACOMONOは枠を自動生成するので全件インポート禁止＝差分削除のみ」）。

→ **同期対象は前日以前の日付に限定する。** 未来日は従来どおりスケジュールとして扱う。

## 解決が要る表記ゆれ

### 講師名（108コマ中26%が装飾つき）

| パターン | 件数 | 例 |
|---|---|---|
| `【講師】` が先頭 | 41 | `【YURI】長町WAACK 初級` |
| `【講師】` が末尾 | 23 | `多賀城HOUSE【AOI】` |
| 括弧なしで先頭 | 13 | `SAYUKI free style` |
| 装飾つき | 28 | `★おっちゃんNJS` / `🔥Ryuki HIPHOP レベルアップWS` |
| 休講 | 3 | `休講【YURI】…` / `【休講】TARO…` |

処理順: 装飾記号（`★🔥🔰` 等）除去 → 休講判定 → `【】` 抽出（先頭/末尾）→
`instructors.name` と別名表で照合。
`【 KEIKO】`（全角スペース入り）があるため trim は必須。

### 会場名

**表記ゆれは今後も起こる前提で設計する**（TARO明示 2026-08-28: スクール側の入力ルールを
まだ固められていない。将来は業務フローで統一したいが、それを待たずに取れるようにしておく）。

同一会場が複数表記で存在する（`戦災復興記念館　展示ホール` と
`仙台市戦災復興記念館　展示ホール`、`コナスポ` と `長町コナスポ` と
`コナミスポーツクラブ 仙台長町, 日本、〒982-...`）。住所が後ろに付く形もある。

→ **別名で正規化する。** 新テーブルは作らず、既存テーブルに JSON配列の列を台帳マイグレーション
（`scripts/migrate.mjs`）で追加する: `studios.name_aliases` / `instructors.name_aliases`。
別名は正規化先の隣に置いた方が保守しやすく、対象も12会場・11名と小さい。
照合は NFKC + 空白除去 + 前方一致。

### 読めなかったものは必ずキューへ

講師名が照合できない、会場が未知、休講か判別がつかない — いずれも
**黙って落とさず「要確認」として画面とメールに出す**。
静かに¥0になるのが金額事故の典型（既存のA-2/A-3も同じ思想で作られている）。

会場未記入のイベントが6〜8月で7件あった（`【 KEIKO】長町ガールズ 初級` など）。
これらは `lesson_master` の既定会場でフォールバックし、**「推測で埋めた」フラグを立てる**。

## 人間のゲート（自動化しない）

TARO決定: **給与の確定(confirm)は人間のまま。** カレンダーの記入ミスがあったときに、
誤った金額が講師へ確定されるのを防ぐ。

自動でやるのは **draft の生成まで**。以降は従来どおり:

```
[自動] 実績同期 → 給与draft生成 → スタジオ料run生成
                          ↓
[人間] 金額を確認 → 確定 → 明細配布 → 講師が確認 → 振込CSV → 銀行で実行
```

振込CSVが明細配布完了までロックされる既存の設計（commit cfe0c7d）は変更しない。

## 併走する課題: 売上3系統のうち口座振替に欠落がある

TARO指摘（2026-08-28）を受けて `hacomono_billing_records` を実査した結果、
**オンライン口座振替の売上が歯抜けになっている**。

| 対象年月 | 振替日 | hacomono側の振替成功額 | billing_records |
|---|---|---|---|
| 202605 | 2026-04-27 | ¥52,200 | ✅ 2026-05-01 |
| 202606 | 2026-05-27 | ¥57,200 | ❌ **無し** |
| 202607 | 2026-06-29 | ¥45,000 | ✅ 2026-07-02 |
| 202608 | 2026-07-27 | ¥59,400 | ✅ 2026-07-30 |

→ **2026年6月の売上が ¥57,200 過小**。カード決済（①②）は毎日の同期で漏れなく入っている。
`billing_date` は「振替結果の取込日」で、hacomono の `/api/purchase/transfers` の
`import_at` と一致する。

欠落の原因は未特定。課金CSVは `HACOMONO_BILLING_QUERY_URL=.../analysis/queries/PL001` を
**UIクリック経路**で取得しており、対象期間が画面の保存状態に依存する。
会員CSVで同種の穴（0件のときエクスポートボタンが描画されない）が2026-08-03に見つかっており、
PL001も**エクスポートAPI直叩きへ移行**すれば期間を明示できて再発を防げる可能性が高い。

これは月次締めの自動化とは独立した課題なので、別タスクとして扱う。
