# 太白区民まつり2026 出演者募集・集計アプリ 設計

- 作成日: 2026-07-22
- 対象: BOOMアプリ (bw5-app)
- ステータス: 設計(TAROレビュー待ち)

## 1. 背景・目的

太白区民まつり2026(2026-10-18(日) 9:30-15:30・杜の広場公園)へ長町クラスで出演申込済。
ステージは **10分の1演目**で、中身が**ジャンル別パート**に分かれる:

- ガールズHIPHOP(担当 KEIKO)
- WAACK(担当 YURI)
- HIPHOP(担当 TARO・KOKEKO)
- 冒頭1分・締め1分は**全員共通**

ジャンル別クラスで振り入れを進めるため、**まず「どのパートに出たいか/その振り入れに参加できるか」を集める参加ヒアリング**を行いたい。
(祭り主催側の運営選考=出演可否とは独立。本アプリは選考を扱わない。)

### やりたいこと(TARO意向)

1. 保護者/生徒が公開フォームで「出演者名」と「希望パート(複数可)」を入力・送信
2. **説明を読んでから申込**の導線(参加費を明記し、内容理解のチェックを通す)
3. 参加者は**送信後も自分で情報を修正**できる
4. 運営は**全体名簿+パート別名簿+人数**をスタッフアプリからいつでも確認
5. 全体リハ・HIPHOPパートの日程は**既存Googleカレンダー(会員公開)へのリンク**で誘導(このアプリで日程は持たない)

## 2. 確定した要件

| 項目 | 内容 |

| 集計 | スタッフ認証必須。全体名簿+パート別名簿+人数 |

## 3. アーキテクチャ判断

### 採用: 既存イベント基盤への統合 + 汎用テーブル

`events` テーブル(code/name/event_date/status)と `/staff/events/[eventId]` 詳細ページが既存。
詳細ページの `<nav>` には「Phase 2で実装」の空カード枠があり、ここに募集・集計カードを追加する。

- 太白まつりを1イベント(code=`TAIHAKU2026`)として `events` に登録
- 募集データは **event_id をキーにした汎用テーブル**で持ち、将来の他イベントでも再利用できる形にする(パート定義・文面はイベント単位の設定)
- 過度な汎用化はしない(選考ステータス管理・多段フロー等は今回作らない)

### 不採用

- **既存 `performers` テーブルの流用**: あれは `m_id`(発表会タイムテーブル番号)前提の**読み取り表示専用**。書込み・パート・同意チェックと構造が合わず、BW5発表会データと混ざるため不可。
- **完全汎用イベント参加基盤**: 8/1締切に対し過剰(YAGNI)。必要になったら切り出す。

## 5. 公開フォーム(認証なし・書込み専用)

- ルート: `/entry/[code]`(太白は `/entry/taihaku2026`)。LINEから開く。
- proxy matcher は `/staff/*`・`/api/staff/*` 等のみ対象で `/entry/*` は含まれない → 既定で公開。
- 新規に作る公開 route/Server Action にはファイル冒頭へ**「なぜ公開か」コメント**を必ず記載(規約4.5)。

### 画面フロー

1. **説明ランディング**
   - `intro_md`(日時/会場/衣装=BOOM T/注意)+ `fee_text`(3,000円)
   - 全体リハ2回・HIPHOPパートの日程 → `calendar_url`(Googleカレンダー)へのリンク
   - **「内容を読み、理解しました」チェック(必須)** を通さないと次へ進めない
2. **申込入力**
   - 出演者名(必須)
   - 希望パート(複数選択可: ガールズHH / WAACK / HIPHOP)
   - 任意メモ
3. **サンクス**
   - 自分の申込内容のみ表示
   - **編集用リンク `/entry/taihaku2026?t=<token>`** を提示 + 端末 localStorage に自動保存 +「このリンクを保管してください」
4. **自己編集**
   - 編集用リンク(トークン一致)で**自分の1件だけ**取得・修正・再送
   - トークン不一致・欠落時は新規申込として扱う(他人の申込は取得不可)

### PII・濫用対策(M22の教訓)

- 名簿を返すGET/一覧/検索APIは**作らない**
- 編集はトークン完全一致の**1件のみ**返す(列挙不可)
- 送信・編集は既存 `checkRateLimit(key, max, windowSec)`(`rate_limits` テーブル)でIP単位のレート制限
- 出演者名など氏名は**ログ非出力**
- 受付OFF(`is_open=0`)時は送信不可

## 6. スタッフ集計(認証必須)

- 画面: `/staff/events/[eventId]/signups`(詳細ページの空カード枠に「出演者募集・集計」カードを追加してリンク)
- API: `/api/staff/events/[eventId]/signups`(既存 `/api/staff/events/*` と同じ `withAuth` パターン)
- 認可: proxy が `/staff/*`・`/api/staff/*` を既にガード。API側も `withAuth` で二重に担保。

### 表示

- サマリー: 総申込数・**パート別人数**(SummaryCard を流用)
- 全体名簿: 名前 / 希望パート / 申込日時 / メモ
- **パート別セクション**: パートごとの出演者一覧・人数
- 操作: **CSV出力** / 行の削除・編集(名寄せ) / 設定編集(`event_signup_settings`: 参加費・締切・説明文・カレンダーURL・受付ON-OFF)

## 7. 実装方針(規約準拠)

- 新規ページは **Server Actions 優先**(規約6)。公開フォームの送信/自己編集は Server Action。
- スタッフ集計の読み書きは既存の API route + `withAuth`(既存 events API と統一)。
- DBアクセスは `src/lib/db.ts` 経由(`getAll`/`getOne`/`execute`/`withWriteTx`)。
- 認証は `src/lib/eventAuth.ts`(`withAuth`/`checkRateLimit`)を流用。
- スタッフ画面は **ブランド3色**(navy/teal/sand)。`StaffPageHeader` を使用。公開フォームはイベント向けの読みやすい配色。
- 破壊的でないスキーマ**追加**のみ(既存テーブル変更なし)。

## 8. スコープ外(今回やらない)

- 運営選考の可否管理
- 全体リハ/HIPHOP日程の管理(Googleカレンダーに委譲)
- 参加費の決済・集金機能
- LINE配信の自動化(告知は別運用)
- 会員番号/HACOMONO突合(入力項目に含めない)

## 9. 受け入れ条件(Doneの定義)

1. `/entry/taihaku2026` で名前+パート(複数可)を送信でき、理解チェック未通過では送信できない
2. サンクス画面に編集リンクが出て、そこから自分の申込を修正・再送できる
3. 名簿を列挙・検索するAPIが存在しない(PII列挙不可)
4. `/staff/events/[eventId]/signups` で全体名簿・パート別名簿・人数・CSV出力・設定編集ができる(認証必須)
5. マイグレーションが本番の `migrate.mjs` で適用できる
