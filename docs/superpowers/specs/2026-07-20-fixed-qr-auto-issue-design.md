# HACOMONO固定QRコード 自動発行＆メール送信（設計）

作成: 2026-07-20 / TARO骨組み承認済み（口頭・2026-07-20）

## 背景・課題

HACOMONOのチェックインはマイページのQRコード（セキュリティのため**30分で失効**）が標準。
スマホを持たない子供は自分でチェックインできない。HACOMONOには**固定メンバーコード**
（失効しないQR）の仕組みがあり、紙に印刷して子供に持たせればタブレットにかざしてチェックインできる。

現状はお客さんから依頼が来るたびに TARO が手動対応:

1. HACOMONO管理サイト → 運営 → メンバー → 対象者 → メンバー詳細
2. 「セキュリティ」タブ → メンバーコード「新規登録」→ **固定メンバーコード用** → 保存する
3. 表示された「有効になったメンバーコード」のQRを、公式LINEで該当メンバーを探して送付

これを**新規入会者は全員自動**にする。既存会員（約180名）への展開は運用が回ってから判断（v1対象外）。

## 決定事項（TARO確定）

- **対象: 新規入会者・全員に自動発行**（依頼ベースにしない＝問い合わせ自体を予防）
- **配送: メール一元化**（公式LINEは会員との紐付けが大変なため使わない）
- **宛先: HACOMONO登録メールアドレス**。ただし**家族（子供）アカウントはダミーアドレスが
  自動発行されている**ため、家族の大元（親）アカウントの実メールアドレスへ送る
- **実行場所: クラウド（GitHub Actions）**。Mac起動に依存しない
- 紛失時の一次対応は「メールを保存しておき再印刷」。無効化を伴う再発行は希望者のみメール連絡

## アーキテクチャ

```
GitHub Actions (毎朝8時台JST cron + 手動実行)
  └─ Playwright: HACOMONO管理にフォームログイン (Secrets: HACOMONO_LOGIN_EMAIL/PASSWORD)
       ├─ 会員リストCSVを直接エクスポート (analysis query export API・daily_sync実証済みの方式)
       │    → bw5-app 既存 sync API へPOST (boom_members 更新 = Mac停止中でも会員検知が動く)
       ├─ bw5-app API に「未発行の新規入会者」を照会
       └─ 各対象者:
            メンバー詳細 → セキュリティ → メンバーコード新規登録(固定) → 保存
            → 画面のQR要素をスクリーンショット (PNG)
            → bw5-app 新API へ member_id + PNG をPOST (x-admin-password 認証)
                 └─ bw5-app: 宛先解決 → メール送信(QR添付・Gmail SMTP=映像予約で実績)
                    → member_qr_issues に記録
```

- **新しい認証情報は増やさない**: HACOMONOログインは daily_sync と同じフォームログイン方式、
  アプリAPIは既存の `x-admin-password` ヘッダー方式
- **毎朝8時台に1回**（GH Actionsの実測遅延60-90分を織り込み、9時前後にメール到着想定。
  入会当日〜翌朝の遅延は許容と TARO 確認済み）
- **⚠️ 最大の未知数 = HACOMONOがGitHub ActionsのIP/ヘッドレスブラウザを弾かないか**。
  実装の最初に**ログイン疎通テストだけの最小ワークフロー**を作って検証する。
  弾かれた場合はこの設計を再検討（フォールバック: 事務所Mac cronに乗せる＝機能は同じ・Mac依存のみ残る）

## 宛先解決ロジック（家族アカウント対応）

1. 対象会員の email がダミー形式か判定
   （**実装時に実CSVでダミーのパターンを確認して確定**。例: hacomono発行の機械的ドメイン）
2. ダミーなら家族の大元（親）アカウントを辿り、その実メールアドレスを宛先にする
   （**家族リンクの取得方法も実CSV列で確認**: 代表メンバー列 or 家族グループ列。
   ML001/ML010 に無ければ HACOMONO クエリの追加列/別クエリを検討）
3. 実アドレスが解決できない場合は**送信せず** `staff_notifications` に「手動対応: 会員ID」を積む
   （誤送信より安全側。個人情報最小化のためログに氏名・アドレスは出さない）

## メール文面（骨子・実装時に清書してTARO確認）

1. これは何か: お子さんだけでも通えるチェックイン用の固定QRです。印刷して持たせてください
2. ⚠️ **他人に共有しないでください**: このQRで他の人がチェックインすると、
   あなたのチケットが消費されてしまいます
3. なくしたら: **このメールを保存しておけば、いつでも再印刷できます**（QRは変わりません）。
   無効化して作り直したい場合はメールでご連絡ください

## データ

新テーブル `member_qr_issues`（台帳マイグレーション経由）:

| 列 | 意味 |
|---|---|
| member_id | boom_members.id (UNIQUE) |
| issued_at | HACOMONO側で固定コードを発行した日時 |
| emailed_at | メール送信完了日時 |
| email_to_masked | 送信先の伏せ字 (例: `a***@g***.com`・トラブル調査用) |
| status | issued / emailed / manual_needed / skipped_existing |

**対象者の定義（重要）**: `enrolled_at >= 稼働開始日` かつ `member_qr_issues` に記録が無い会員のみ。
稼働開始日カットオフが無いと既存会員約180名が「未発行」として一斉対象になってしまうため必須。
カットオフ値は定数で持ち、既存会員へ展開する時はこの値を動かすだけで対応できる。

- **QR画像・コード値は保存しない**（メール添付のみ。DB/GHログ/リポジトリに残さない）
- 既にHACOMONO側で固定コードが存在する会員（TARO手動発行済み）は発行スキップし
  `skipped_existing` 記録（重複発行しない）
- 失敗した会員は記録が残らない → 翌朝の実行が自動リトライ

## 非対象（YAGNI / v1でやらない）

- 既存会員約180名への一斉/希望制発行（運用が回ってから判断）
- 公式LINEでの配送・Lstep連携
- QRの自前生成（HACOMONO画面のQR画像をそのまま使う）
- 無効化・再発行の自動化（依頼ベースで手動）

## 実装順

1. **HACOMONOクラウドログイン疎通テスト**（最小ワークフロー・ここが崩れたら設計再検討）
2. 発行の自動操作（Playwright: セキュリティタブ→固定コード発行→QR画像取得）
3. bw5-app 側: member_qr_issues 台帳マイグレーション + 受信API + 宛先解決 + メール送信
4. GH Actions 本組み（cron + Secrets）+ 実会員1名でのエンドツーエンドテスト（TARO立会い）
5. FAQ登録・memory/STATE.md記録・メール文面清書のTARO確認
